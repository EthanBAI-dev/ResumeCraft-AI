# Day 20 · AI Diff 审阅：模型只能提建议，不能直接改简历

## 今天完成了什么

把已有的结构化 AI Route 接到了经历要点编辑器。每次改写会先进入独立的待审队列，原文保持不动；用户可以逐条接受、拒绝、全部处理、重新生成，或在请求尚未结束时主动停止。接受建议仍然走 `resume-store.updateItem`，因此会自然进入原有撤销历史。

## 决策

### 待审状态单独放进 `ai-store`，不塞进简历 Schema

备选方案是把 `pendingSuggestion` 挂到每个 highlight 上。那样持久化、导出、模板渲染和 ATS 文本提取都会被迫认识一种临时 UI 状态。最终选择独立 store：简历仍然只保存用户确认过的事实，AI 队列则按 `sectionId:itemId` 定位目标。

代价是接受建议时需要把目标索引映射回当前条目。为避免空白要点被过滤后索引错位，请求前同时记录原始索引；AI 新增的额外要点统一追加，而不是覆盖已有内容。

### 用短文本 LCS 做词级 Diff

备选方案是直接按字符标色，或引入通用 diff 包。字符 diff 在中文改写时噪声太大；通用依赖对 300 字以内的要点又显得过重。当前实现用 `Intl.Segmenter` 分词后做 LCS，并把连续同类片段合并。复杂度为 O(n×m)，但 Schema 已把单条要点限制在 300 字以内，因此边界可控。

## 踩坑

AI 请求发送前会过滤空白要点。如果直接用过滤后数组的索引回写，`["", "第二条"]` 的建议会错误覆盖第 1 个空白框。修复方式不是在 UI 猜位置，而是在进入请求时保留 `sourceIndex`，并写了回归测试锁住这个映射。

另一个边界是“重新生成后旧请求迟到”。store 为每次请求生成 `requestId`，完成或失败 action 只接收当前 ID；旧响应即使晚到也会被忽略。
