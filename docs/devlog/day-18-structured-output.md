# Day 18 — Zod 结构化输出与服务端边界

日期：2026-08-17
阶段：P4（完成）

## 今天交付

- 新增通用 `generateAiObject`，接受任意 Zod Schema，并复用统一 Provider、超时、取消、错误归一化和用量仓库。
- 五类简历 Prompt 接入 `ResumeAiOutputSchema`，成功结果保证包含 1–20 条、单条不超过 300 字的 `highlights`，以及最多 12 条 `missingFacts`。
- 结构校验失败默认额外生成 1 次，可通过 `AI_SCHEMA_RETRIES` 在 0–2 次之间调整；修复成功时累计整条调用链的 token。
- 新增 `POST /api/ai/resume`：用判别联合校验五类请求，限制 JD / 原始经历为 12,000 字、条目为 20 条，再把浏览器取消信号传给模型调用。
- API 只返回稳定错误码、可重试标记和安全消息，不透传 Provider 原始响应或异常 cause。

## 决策

### 遵循 AI SDK 6 当前接口，不照抄路线图里的弃用 API

本地安装版本已把 `generateObject` 标记为 deprecated，并推荐 `generateText + Output.object`。两者都能得到 Schema 驱动的对象，但新接口与文本、工具和后续流式 API 使用同一生成入口。现在按本地类型声明实现，同时更新路线图，避免刚交付就背上弃用债。

### 抽取执行内核，而不是复制一套结构化调用

文本与对象生成都需要 Provider 解析、超时、重试、用量与错误记录。复制 Day 16 的代码会让两条路径迟早出现不同的计量口径，因此抽出 `executeAiRequest`；文本层只把 `text` 映射为通用 `value`，结构化层映射为经过 Zod 解析的对象。代价是本日必须重跑原有文本生成回归测试。

### Schema 修复重试与网络重试分开计数

`AI_MAX_RETRIES` 处理限流或瞬时网络故障，`AI_SCHEMA_RETRIES` 处理模型已经响应、但对象不合法的情况。两者混成一个数字会让调用成本不可预测；结构修复最多限制为 2 次，并在最终失败时返回 `invalid_response`。

### Route 不接受客户端指定模型

当前还没有账号、套餐和配额层。若直接让请求体携带任意模型，浏览器调用者就能选择更昂贵的 Provider。Route 只使用服务端 `AI_DEFAULT_MODEL`；以后做用户套餐时再把模型选择变成服务端策略。

## 踩坑

Route 错误测试发现 `instanceof AiError` 在模块被测试运行器或服务端构建加载为不同实例时可能失效，稳定的 429 会掉进未知错误分支。现在使用同时检查 `name / code / retryable / status` 的 `isAiError` 类型守卫，且 `normalizeAiError` 也复用它，跨模块仍能识别已经归一化的错误。

另一个容易忽略的问题是结构修复会产生额外费用。首次对象无效、第二次成功时，如果只记录最后一次 usage，会系统性低估 token；现在成功链路会合并每次生成的输入、输出、缓存和推理 token。
