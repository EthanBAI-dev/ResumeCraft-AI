## 1. 命名

仓库目录已定为 **ResumeCraft**，全部文档沿用。

> 你在需求里更偏好 `CareerCanvas AI`。我建议保留 ResumeCraft，理由有二：
>
> 1. **Canvas 会误导产品预期** —「画布」暗示自由绝对定位，而简历必须是 A4 流式分页布局。名字承诺了做不到（也不该做）的事，见下节。
> 2. Craft 语义正好对应我们的核心卖点：约束下的精细打磨。
>
> 如果仍想改名，成本是一次全局替换 + 目录重命名，任何时候都能做。

## 2. 关键定位纠偏：**不是 Figma，是"约束式结构化编辑器"**

需求里写的是「类似 Figma 的可视化编辑」。**这个方向要收窄**，否则项目会死在分页和 ATS 上：

| 自由画布（Figma 模式）            | 实际后果                                                              |
| --------------------------------- | --------------------------------------------------------------------- |
| 元素绝对定位                      | 内容一变长就重叠/溢出，用户每次改字都要手动挪位置                     |
| 无文档流                          | 分页要自己算，跨页断行是地狱级难题                                    |
| 导出 PDF 时文字变成多个孤立文本框 | **ATS 解析顺序错乱 → 简历直接被机器判死**（这是简历工具的第一性问题） |

**我们采用的模型：结构化流式布局 + 块级拖拽 + 网格约束**

```
A4 页面
├── 栏布局（1 栏 / 主栏+侧栏 7:3 / 对称 5:5）  ← 可拖动分隔线调整
│   ├── Section（工作经历）        ← 可拖拽跨栏、跨页排序
│   │   ├── Item（某段经历）        ← 可拖拽排序
│   │   └── Item
│   └── Section（技能）
└── 自动分页（内容溢出自动进下一页，实时显示分页线）
```

用户获得的自由度：**顺序、分栏、显隐、间距、字号、配色、模板**——足够「所见即所得」，但排版永远不会崩。这是 Notion / Framer 的思路，不是 Figma 的。

> 简历上仍然可以写「可视化拖拽编辑器」，因为它确实是。只是内部实现讲的是「约束求解」而不是「自由画布」——面试时这反而是加分项。

## 3. 功能范围

### 3.1 MVP（必须有，缺一个项目就不成立）

| #   | 功能                      | 验收标准                                                 |
| --- | ------------------------- | -------------------------------------------------------- |
| F1  | Schema 驱动的结构化编辑器 | 6 类区块（基本信息/工作/项目/教育/技能/证书）可增删改    |
| F2  | 实时 A4 预览              | 输入到预览更新 < 100ms；真实分页；溢出高亮               |
| F3  | 区块拖拽排序 + 跨栏       | 拖动有落位指示；键盘可操作（a11y）                       |
| F4  | 模板系统                  | ≥3 套模板，切换不丢数据，1 秒内生效                      |
| F5  | PDF 导出                  | 与屏幕预览像素级一致；文字层可选中可搜索                 |
| F6  | AI 内容引擎               | 润色/扩写/缩写/翻译/生成；结果落回结构化字段；可逐条接受 |
| F7  | ATS 评分                  | 输出 0–100 分 + 分项 + 每条可点击定位到问题位置          |
| F8  | 本地持久化                | 关掉浏览器不丢数据（IndexedDB），无需登录                |

### 3.3 V2（加分项，时间够再做）

- 简历 PDF 反向解析导入（自研，**不碰 OpenResume 代码**）
- 模板市场 / 用户自定义模板 JSON
- 协作评论

### 3.4 **明确不做**（写下来是为了防止自己失控）

| 不做                           | 原因                                                 |
| ------------------------------ | ---------------------------------------------------- |
| 自由画布 / 绝对定位            | 见第 2 节                                            |
| 富文本所见即所得编辑器（自研） | 用 Tiptap，不重造轮子                                |
| 求职投递 / 岗位爬虫            | 与核心价值无关，且有合规风险                         |
| 移动端编辑                     | 简历编辑是桌面场景；移动端只做**只读预览**           |
| 多人实时协同（OT/CRDT）        | 成本极高、演示价值低。版本管理已经能讲同样的技术深度 |
| 自建大模型 / 微调              | 用 API。项目亮点在工程编排，不在模型                 |

## 4. 目标用户与场景

主场景：**校招/社招求职者，投递前 3 天，手里有一份 Word 简历和一个 JD。**

用户旅程（这条线决定了首页的三个 CTA）：

```
导入/从零开始 → 填内容（AI 帮写）→ 粘贴 JD → 看 ATS 分数 → 按建议改 → 导出 PDF → 投递
```

每个环节都要能在 **60 秒内**看到价值反馈，否则用户流失。

---

## 5. 成功判据

这是个作品集项目，成功 = **能在 5 分钟内向面试官演示完，并经得起 3 个追问**。

演示脚本（P7 阶段要录成 90 秒视频）：

1. 粘贴一段大白话工作经历 → AI 一键结构化 + 量化改写，diff 逐条接受
2. 拖动区块换布局 → 实时分页
3. 粘贴 JD → ATS 分数从 62 跳到 88，点开每一项看原因
4. 导出 PDF → 当场用 pdf.js 把文字抽回来证明机器读得出

3 个必经追问及答案见 [05 简历话术与面试问答](05-resume-pitch.md)。
