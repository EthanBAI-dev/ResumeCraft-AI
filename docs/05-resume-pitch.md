## 1. 简历条目

### ResumeCraft · AI 驱动的可视化简历设计平台

`Next.js 16 / TypeScript / Zustand / dnd-kit / Zod / Vercel AI SDK / Playwright / Prisma / PostgreSQL`
[在线体验](#) · [GitHub](#)

一个 Schema 驱动的在线简历设计平台。用结构化拖拽编辑替代模板填空，用大模型完成内容生成与量化改写，并通过 PDF 文本回读校验保证简历能被 ATS 正确解析。

- 设计 Zod 单一 Schema 作为全项目真相源，同时驱动 **TS 类型、表单校验、API 契约与 LLM 结构化输出**，消除跨层类型漂移
- 用三维数组 `layout[页][栏][区块]` 统一建模布局，将拖拽排序、跨栏移动、分页塌缩为对同一数据结构的操作，新增模板零成本 <!-- P2 -->
- 基于 dnd-kit 实现跨栏跨页拖拽，支持键盘操作与屏幕阅读器播报，Lighthouse A11y ≥ 90 <!-- P2 -->
- 自建 Playwright + Chromium 导出服务，实例池化将 PDF 生成 P95 从 __ms 降至 __ms；**HTML/CSS 单一渲染源保证预览与导出零差异** <!-- P3 -->
- 设计 **PDF 文本回读校验**：导出后用 pdf.js 反向抽取文本与源数据比对，将「ATS 友好」变成可回归的量化指标（覆盖率 __%，已进 CI）<!-- P3 -->
- 封装多模型 Provider 抽象层（Claude / GPT / DeepSeek / Gemini），基于结构化输出让 LLM 直接产出合法 Schema 对象，配合 Cursor 式 **inline diff 逐条审阅**，杜绝 AI 静默覆盖用户内容 <!-- P4 -->
- 实现 ATS 规则引擎：__ 条可插拔纯函数规则 + JD 关键词 TF-IDF 匹配，输出四维加权分数与**可点击定位到具体字段**的改进建议 <!-- P5 -->
- 版本管理采用 RFC 6902 JSON Patch 增量 + 周期性快照，相比全量存储降低存储 __%，并支持任意版本还原与结构化对比 <!-- P6 -->

> 空格 `__` 是留给真实数据的。**编不出来的数字就把那条删掉**，不要填一个好看的假数字。

## 2. 三个差异化亮点（面试时主动抛的那三个）

普通简历项目讲的是"我接了 GPT 的 API"。这个项目要讲的是这三个：

### ① PDF 文本回读校验

> "简历的第一个读者是机器。市面上所有简历工具都说自己 ATS 友好，但没有一个验证过。我在导出流水线里加了一道回读：生成 PDF 后用 pdf.js 把文字抽回来，跟源数据做覆盖率和顺序一致性比对，覆盖率低于 95% 就告警并指出是哪个区块出的问题。这个检查现在跑在 CI 里，三套模板 × 三种内容长度做回归。"

**为什么加分**：把营销话术变成工程指标；体现了"从用户真实场景反推技术方案"的思路；有测试、有 CI、有数字。

### ② LLM 结构化输出 + Diff 审阅

> "AI 功能的难点不是调 API，是两件事。第一，输出必须能直接落回数据结构 —— 我让模型直接产出符合 Zod Schema 的对象，校验失败自动重试，不用写任何解析代码。第二，AI 不能静默覆盖用户内容 —— 结果先进 pending 队列做词级 diff，用户逐条接受或拒绝，接受了才写入并记入版本历史。这是从 Cursor 的交互范式学来的。"

**为什么加分**：区分了"会调 API"和"会做 AI 产品"；结构化输出复用了 Schema 单一真相源的架构红利，能顺势讲整个架构。

### ③ 约束式编辑器（反 Figma）

> "需求最初想做成 Figma 那样的自由画布，我否决了。绝对定位的元素导出成 PDF 后是一堆孤立文本框，ATS 抽出来的阅读顺序是乱的 —— 这恰好毁掉产品的核心价值。所以改成结构化流式布局加块级拖拽，自由度用分栏比例、间距、模板这些参数来补偿。"

**为什么加分**：**主动砍需求并说清代价**，是资深工程师最稀缺的信号。

## 3. 面试官一定会问的问题

### Q1：这跟 Reactive Resume 有什么区别？你是不是照抄的？

坦诚 + 划界：

> "Reactive Resume 是我主要的参考，它的 `layout[页][栏][区块]` 三维数组设计我直接采用了，这个在我的 ADR 文档里有注明来源。它是 MIT 协议，允许这么做。
> 但有三点是我自己的：一是它的 AI 只是弹窗改文本，我做的是结构化输出加 diff 审阅；二是它没有 ATS 评分，我做了规则引擎；三是它 v5 用客户端 react-pdf，我用无头 Chromium 打印同一份 DOM，保证预览和导出零差异 —— 这个我在 ADR-001 里权衡过，代价是要多部署一个 Docker 服务。
> 另外 OpenResume 我只读没抄，因为它是 AGPL-3.0，复制代码会传染整个项目。"

**这个回答的杀伤力在于**：它同时展示了技术判断力、文档习惯和**开源许可证意识** —— 最后一点是绝大多数候选人的盲区。

### Q2：实时预览会不会卡？你怎么保证性能？

> "会，而且第一版就卡了。原因是每次按键都触发整棵简历树重渲染。做了四件事：输入框受控于 local state，200ms debounce 后才写 store；预览里每个 Section 用精确 selector 只订阅自己那一片；React.memo + 稳定 key；数据 store 和 UI store 分开，避免「打开面板」这种操作也进撤销历史触发更新。
> 现在按键到预览更新的 P95 是 __ms，这个数字打在 CI 里，超了就 fail。"

_(P1 Day 5 会拿到真实的前后数字，回来填。)_

### Q3：版本管理为什么不直接每次存一份 JSON？

> "简历 JSON 是 20–50KB，改 100 次就 5MB，而且全量存储回答不了「这两版差在哪」。所以用 immer 的 `produceWithPatches` 直接产出 RFC 6902 patch，每 50 个 patch 或用户手动命名时打一个全量快照做检查点。还原就是从最近快照正向 apply。
> 这个的风险是还原逻辑写错就是静默数据损坏，所以写了一个随机测试：随机生成 500 次操作，随机点回滚，断言结果跟全量存储逐字节一致。"

### Q4：ATS 评分是怎么算的？你怎么知道它准？

**诚实是唯一正确答案**:

> "我不知道它准 —— 真实 ATS 是黑盒，任何声称能预测通过率的产品都在营销。所以我刻意不叫「通过率预测」，叫「可解析性与内容质量评分」。
> 四个维度加权：可解析性 30%（联系方式能否正则抽出、日期格式、PDF 回读覆盖率）、内容质量 35%（强动词开头、量化指标占比、bullet 长度）、JD 匹配 25%、完整性 10%。JD 为空时第三维不计入，按剩余权重归一化。
> 关键设计是**每一分都可解释**：分数旁边能展开看到具体是哪条经历扣的分，点一下直接跳到编辑器对应字段。引擎是纯函数，零 IO，所以每条规则都有正反例单测。"

### Q5：如果用户量涨到 10 万，哪里先崩？

> "PDF 导出服务。它是有状态的(Chromium 常驻），内存是瓶颈不是 CPU，单实例并发我用信号量卡住了。扩容路径是把它改成消息队列消费者，导出变成异步任务，前端轮询或 SSE 拿结果，worker 水平扩。
> 第二个是 AI 接口成本，现在用 Upstash 按用户限流 + 相同输入 hash 缓存，再涨就得做配额和付费墙。"

### Q6：你在这个项目里最大的失误是什么？

准备一个**真实的**答案，从日记的「踩坑」里挑。不要说"没有失误"，也不要说"我太追求完美"。

日记写好了，这题就有素材。这也是为什么 [DEVLOG](../DEVLOG.md) 要求踩坑必须写到根因。
